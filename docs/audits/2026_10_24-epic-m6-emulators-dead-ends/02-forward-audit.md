## Findings, written as each row is read

### F-01 (Q6, Q4, Q5, Q7; Renovation; the 81 LibreELEC files): Kodi's RetroPlayer set, which nothing builds, comes back with every merge of LibreELEC master

81 files under `packages/emulation/` (2,258 lines, 86,663 bytes): 77 `libretro-*` cores, `cyclone68000`, `libretro-common`, and `rcheevos` with its cmake file.
- **What reaches them.** Their only build edges are 79 lines in the 78 Kodi `game.libretro*` addon recipes, themselves `unreached`. No shipped plan, metapackage list or root holds one.
- **How they keep coming back.** They arrive through ROCKNIX's merges of LibreELEC master; the last on our base, `c12efbd574` (2026-08-12), carries LibreELEC's `d43d166b7a`. LibreELEC master moves them still. Of the 80 recipes:
  - 61 differ from master by an added version-stamp hunk;
  - 6 pins have moved;
  - so the next merge rewrites at least 67 of the 80.
- **Twins.** 67 have a ROCKNIX `*-lr` twin by name or by source, and 10 have none.
- **Disposition.** `kept: upstream's; #585 candidate`. The remedy is ROCKNIX's to choose (brief § 2): stop carrying `packages/emulation/` for a distribution that ships no Kodi. The coordinator posts the proposal; this lane writes its counts (PL-01).

### F-02 (Q6; Renovation; the five ROCKNIX recipes): ROCKNIX's own cores that no shipped device builds

- `boom3-lr` and `vitaquake3-lr` are built only through `idtech-lr`'s `x86_64` arm (`idtech-lr/package.mk:20-22`). GENERIC_X64 skips `idtech-lr` (`virtual/emulators/package.mk:111`), so only ROCKNIX's AMD64 image builds them, and pixelelated ships none.
- `mame2003-lr`, `panda3ds-lr` and `play-lr` have no build edge from any file. `play-lr` left the metapackage's `LIBRETRO_CORES` in upstream's `20b7d7ea02` (2025-10-26, *buildroot: cleanup AMD64*). `panda3ds-lr` and `mame2003-lr` are named by no other file in the history since ROCKNIX's import `9f1fab30f6`.
- **Disposition.** `kept: upstream's; no shipped device builds it`, citing T3's `04` § Q6 at `b3cb4ec8c5`, which named exactly these five. The three that no ROCKNIX configuration builds at all are a #585 line: dead in ROCKNIX itself (PL-02).

### F-03 (Q6, Q7; Low; Renovation; a fork-own line outside the slice): the image's `core-pins` names two cores no shipped image carries

`virtual/emulators/package.mk:1768` (fork commit `3a56a04f8b`, #21) lists `boom3-lr` and `vitaquake3-lr` in `IDTECH_CORES` on every device. The `core-pins` loop writes a row for each recipe it can read a version from, so every shipped image's `/usr/share/rocknix/core-pins` carries both rows, while no image holds either `.so` (P10, P11).
- **The one reader** is `cloud_capture:121`, which looks up the core that ran. These two never run on a pixelelated image, so no manifest names them and nothing is wrong at run time.
- **The cost** is a table that lists what the image does not hold. That is the kind of record `engineering-practices.md` § A name is not a behaviour warns about.
- The line is T3's (the metapackage, accepted). This lane changes nothing there. The disposition is the coordinator's: route it as a one-line condition on `TARGET_ARCH` beside `idtech-lr`'s own, or withdraw it as harmless (PL-03).
