## 6. What the first reader missed

**G-30 — new — `tools/cloud-round-trip:6841-6847,5506,7091,7721-7725,7801-7808`.**  
**KILL1 has an unhandled `NameError`: `webdav` is undefined in `fx_kill1()` at line 6846.** The variables with that name in `Link.exercise()` and KILL5 are local to those functions and cannot supply it. Any KILL1 execution reaching that line aborts instead of completing the fixture; the runners catch `Fail`, not `NameError`. Thus A5 and RETENTION are not the only cells whose present implementation prevents an ordinary completed green run.

**G-31 — new — `tools/cloud-round-trip:4717-4740,4843-4857`.**  
CONTRACT’s copy-arm conflict detection agrees with its own text: an ordinary dry-run output always includes the literal word **`conflicts`**, even when the list is empty. The guard tests whether `"conflict"` occurs in that output, so on the intended nonempty setup a classifier that completely misses the conflict still passes the “reported conflict” and “guard fired” checks. Since that same guard suppresses the wet run, “neither file changed” then provides no corrective evidence. Check the structured conflict collection and require the expected conflicting path instead.

**G-32 — new — `tools/cloud-round-trip:313-316,440-445,553-562,588-620,2480-2493,7705-7717`.**  
A requested suite can do no relevant work and finish **PASSED**: `--only A1` without a second device merely prints an instruction, and an unknown `--only` name is not rejected. KILL cells missing their prerequisites are skipped without increasing failures or adding to the final skip summary. Separately, equipment checks in both preparation functions discard `check()`’s return value, so those printed FAILs need not affect the exit status; the normal equipment condition does not even require the `cloud_restore` name it queried. These are verdict-accounting gaps, not merely absent totals.

**G-33 — new — `tools/cloud-round-trip:1484-1494`.**  
Step 25’s “every ES path is carried by exactly one tier” can pass when the path-extraction probe produces **no paths at all**: errors upstream of the final pipeline are not turned into a failed assertion. Even with valid input, it skips every `/storage/roms/*` path and searches for remaining path strings in the backuptool source. A matching comment can satisfy that search, and no uniqueness or actual archive-membership test is performed. Its PASS certifies only “this text search emitted no orphan names.”

**G-34 — new — `tools/cloud-round-trip:4452-4455,6745-6750`.**  
CAP13’s warning assertion has a concrete false-positive: `grep -c ... || echo 0` yields **`0\n0`** for an existing log with no matches. After `.strip()`, that value is neither `""` nor `"0"`, so `warned not in ("", "0")` passes while no warning exists. It also searches the whole log rather than this invocation’s suffix. The file already documents and avoids this exact double-zero trap in `Kill.count_in()`.

**G-35 — new — `tools/cloud-round-trip:6815-6825,6844-6853`.**  
KILL1 classifies a missing old file as `"absent"`, but constructs `torn` from only states beginning with `"TORN"`. Consequently, **deleting every cloud copy can pass “every file … is v1 or whole v2,”** even on the atomic backend. A subsequent successful retry can restore v2 and conceal that the promised post-cut preservation property failed. This is broader than the listing-error problem: an accurate empty listing also exposes the defective predicate.

**G-36 — new — `tools/cloud-round-trip:5212-5218,6367-6372,6472-6485,6494-6501,7035-7040,7221-7234,7544-7549,7559-7576`.**  
The kill-point witnesses do not reliably prove a kill occurred: the watcher writes `landed` even if no PID was available or `kill` failed, and it tests its condition before testing the completed-run receipt. Likewise, `wait_marker()` accepts a retained progress marker before checking whether the run already ended, while `kill_group()` can succeed because the group was already gone. KILL4 watches a growing **final-name** tar, so a writer that publishes only after completion can satisfy the condition after tar has finished; an empty `truncated` set then makes its invalid-upload check vacuous. KILL11 requires no kill receipt, and KILL16 explicitly kills before the write, so neither should be credited as proof of an interrupted write’s atomicity.

**G-37 — new — `tools/cloud-round-trip:4432-4438,6196-6199,7453-7459,5323-5334`.**  
CAP13 sleeps 50 ms and ignores failure of the SIGTERM send; if capture already finished, the normal completed result still passes “SIGTERM was ignored.” KILL13’s purported **0 ms** cut is not zero-delay: `mon.sendkey("z")` itself sleeps the default 150 ms before returning to the reset call, in addition to monitor-command latency. Finally, `settle()` treats two equal fingerprints three seconds apart as completion, although a stalled upload can be unchanged over that interval and resume later. These should be reported as measured sampling windows or replaced with explicit lifecycle witnesses, not treated as established orderings.

**G-38 — new — `tools/cloud-round-trip:1659-1671,1891-1895,5904-5934,2224,2302`.**  
The common vocabulary gate accepts **any** permitted outcome sentence; it does not require `Skipped` for 69/75 or `Couldn't finish` for a failure. Thus exit 69 with `Completed.` can satisfy the no-network message checks, and a failure sentence beginning `Completed` can pass if it contains recovery wording. Step 29 similarly does not assert “rclone’s code”: it accepts any result other than 0 or 69, including a lock refusal, missing-command status or `run_rc()`’s `-1` transport-failure result. Also, A9/A12 call `assert_message()` without enabling its default-false vocabulary argument, despite the broader header promise of default vocabulary checking.

**G-39 — new — `tools/cloud-round-trip:5990-5996,6024-6033,6073-6087,6135-6141`.**  
The litter scan’s “one record each” label exceeds its validation: a lone correctly named manifest is not parsed, and a lone malformed `last-capture` line can satisfy the duplicate-mode test. An empty live ES settings file is converted to `{}` rather than rejected, provided the separate record checks pass. Its `device.json` duplicate-name branch cannot fire on an ordinary unique-path filesystem/current-object listing: that listing contains at most one identical path. The scan can detect particular filenames, counts and some formats, but not general last-known-good validity or all duplicate-record mechanisms.

**G-40 — new — `tools/cloud-test-backend:593-626,648-654`.**  
`reset` can falsely certify “endpoint is empty”: filesystem removal errors are ignored, its hidden-file glob omits names beginning with two dots, and surviving S3 objects produce at most a warning before the unconditional success message. This weakens the clean-prestate premise behind many subsequent positive and absence checks. The S3 `cat` guard is better than bare `rclone cat`, but it asks whether **anything** is listed at the supplied path, not whether the exact requested key exists; a directory/prefix with children is not the same object. Keep the missing-key improvement, but narrow its certificate to the actual probe it performs.

**G-41 — new — `tools/cloud-test-backend:177-179,196-202,488-496,507-519,525-537,542-543,582-590,675-695`.**  
Endpoint health is unevenly established: PID checks prove only that a PID exists, and `wait_port()` proves only that some listener has the port. FTP performs no login/read probe, and SMB’s comment promises a share-list test while the implementation only searches a startup log; the new SFTP startup path genuinely does test a login. Already-running branches can bypass even those startup checks. The final `down` test also treats a failed `ss` probe like absence, so successful command status alone is not a cleanup certificate.

**G-42 — new — `tools/cloud-test-backend:137-139,373-398,516-521,722-733`.**  
The host key is **not** the private key emitted into the guest stanza: the code distinguishes `SFTP_HOSTKEY` from the client `SFTP_KEY`, and explicitly sets both to mode 600. The serious boundary is that the exported client key authenticates as the host’s real user to an **unchrooted** internal-SFTP service; `-d DATA` sets a starting directory, not a filesystem jail. A guest holding that key can therefore access other paths permitted to that host user through this service, notwithstanding the forced SFTP-only command. Host authentication is also deliberately disabled in the startup probe and guest stanza, so “throwaway cloud credentials” should not be read as “no host credential or trust risk.”

**G-43 — new — `tools/cloud-test-backend:90-93,158-174,432-449,481-485,531-554,699-763,884-892`.**  
Credential serialization fails open in places: WebDAV/SMB/FTP stanza generation falls back to printing the clear password if `rclone obscure` fails, while the first S3 host-config write occurs before its mode-600 chmod and without a private umask. Passwords also appear in server/container invocation arguments, so these facilities should remain synthetic-credential-only even when environment overrides are used. Shell argument quoting does not solve the other grammars: SMB’s semicolon-delimited account argument and the unescaped generated shell/config text in `seed-device` can break on delimiter-bearing overrides. Validate or encode those values for their destination grammar, and refuse stanza generation when credential conversion fails.

**G-44 — new — `tools/cloud-round-trip:915-918,615-617,7773-7786,5186-5189,6415-6419`.**  
There is a destructive ownership bug behind the advertised scratch-tree safety: step 8 refuses an occupied `/storage/roms/vectrex`, but `finally` still invokes cleanup, which unconditionally removes that directory when `--real-roms` is false. Thus the **refusal path can delete exactly the library it refused to use**. LINK and KILL resets also remove that directory without establishing ownership. Track directories created by this run; neither a fixed fixture name nor `--real-roms` being absent establishes that the harness owns existing contents.

**G-45 — new — `tools/cloud-round-trip:4545-4568,3063-3067,7747-7799,615-620`.**  
Cleanup success is not included in the verdict: restoration commands often ignore status, and a caught restoration failure emits WARN without increasing the failure count. Cache snapshotting is especially brittle: tar failure is suppressed before destructive fixtures run, and restoration treats any nonempty archive as sufficient to delete the current cache, attempts extraction unchecked, then removes the archive. A partial snapshot can therefore lose the original state while the test still ends PASSED. Validate the snapshot before destructive work and make inability to restore an explicit unsuccessful outcome.

**G-46 — new — `tools/cloud-round-trip:145-148,855-860,2850-2867`.**  
A15 still plants **plain text named `.tar.gz`** for the upload that is supposed to prove the healed destination and old-marker handling. Elsewhere this same harness explicitly explains that such fixtures are rejected by archive validation and replaces them with real tar archives. Against an uploader honoring that validation, A15 fails before testing the identity/marker behavior it names. This is another stale-fixture failure, not another `cloud_reconcile` dependency.

**G-47 — new — `tools/cloud-round-trip:6408-6409,7094-7100,7150-7153,820-833`.**  
KILL5 reads `CLOUD_BACKUP_KEEP` for its message but plants three own archives and always expects exactly three after retry. A correct implementation configured to keep two or five can fail this fixture, while an implementation incorrectly hard-coded to three can pass its stated configured-retention claim.
