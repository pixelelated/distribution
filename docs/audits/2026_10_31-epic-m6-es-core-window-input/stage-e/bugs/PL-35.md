## Code trace

**Where (at `16dbac5211`):** `PowerSaver.cpp:15`, `:19-36` (`pushRefreshEvent`, `resetRefreshEvent`); `PowerSaver.h:68` against `Window.cpp`'s `postToUiThread` (the worker's push) and `es-app/src/main.cpp:1194` (the interface thread's reset)

**The defect:** `pushRefreshEvent` reads and writes the static `mHasPushedEvent` (`:21`, `:30`) and runs on any thread that posts to the interface (`Window::postToUiThread`); `resetRefreshEvent` writes it (`:35`) on the interface thread each time the main loop's `SDL_WaitEventTimeout` returns an event. The flag is a plain `bool` with no lock or atomic between the two: a data race, so a push can be skipped or doubled, and the main loop may sleep through a post until its timeout.

**How it was found:** T35's audit (#682), stage E S2, read beside PL-26's wake (`stage-e/s2-checks.txt`, a lead); disposed by the coordinator under D-WORKFLOW-132 and rule 6 (#682 comment 6546220910): a `bug`, the atomic fix only if a ThreadSanitizer program shows the race at the pin. Not in `05` at stage D; added as PL-35.

**The positive before the fix:** `SAN tsan-powersaver (-fsanitize=thread): rc 66; WARNING: ThreadSanitizer: data race` (`stage-e/s9-before.txt`, `stage-e/tsan-powersaver.cpp` over `PowerSaver.cpp:15-36` and `PowerSaver.h:68-69` lifted verbatim): the interface thread's write in `resetRefreshEvent` against the worker's read in `pushRefreshEvent` (`x_ps_push.inc:8`, `PowerSaver.cpp:21`).

**What reading cannot prove:** how often a post lands while the main loop resets the flag on a device, and what a skipped wake costs there (the power saver's timeout).

**Can this be done on the VM?** Yes -- host-only (the ThreadSanitizer program in `tools/t35-build-tests.sh`).
