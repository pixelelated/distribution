## Code trace

**Where (at `16dbac5211`):** `Window.cpp:1284-1288` (`postToUiThread`) against `:540` (`update`), `:778` (`render`), `:1111` (`cancelScreenSaver`)

**The defect:** `postToUiThread` runs on worker threads and, under `mNotificationMessagesLock`, sets `mSleeping = false` and `mTimeSinceLastInput = 0`. The interface thread adds to `mTimeSinceLastInput` in `update` (`:540`), compares it in `render` (`:778`) and zeroes it in `cancelScreenSaver` (`:1111`) without that lock. A data race: the idle counter can be reset, kept or torn, so the screensaver may start or stay off for the wrong reason.

**How it was found:** T35's audit (#682): the independent seat's G-2, verified at the pin; PL-26 in `docs/audits/2026_10_31-epic-m6-es-core-window-input/05-punch-list.md` and #1337. Low: the consequence is an idle counter reset or kept.

**The positive before the fix:** Read at the pin. The case is written first in stage E's S2: `stage-c/tsan-posts.cpp` extended with `postToUiThread`'s writes against `update`'s read, which reports the race at the pin.

**What reading cannot prove:** how often a post lands in the same frame as the idle check on a device.

**Can this be done on the VM?** Yes -- host-only (the ThreadSanitizer program in `tools/t35-build-tests.sh`).
