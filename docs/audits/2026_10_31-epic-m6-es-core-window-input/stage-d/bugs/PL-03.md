## Code trace

**Where (at `16dbac5211`):** `Scripting.cpp:88-149` (`:92-93`, `:95-96`, `:98-113`); `utils/Platform.cpp:162-181`

**The defect:** `executeScript` builds one shell command line: the script path is quoted only when it contains a space (`:92-93`), the event name is appended bare (`:95-96`), and each argument has every double quote stripped (`:107`) and is quoted only when it contains a space -- then in double quotes, where `$( )`, backticks and parameter expansion stay live (`:109-112`). `ProcessStartInfo::run` hands that line to `system()` when it waits and to `/bin/sh -c` otherwise (`Platform.cpp:162-181`, T36's). So shell metacharacters in an argument a caller passes -- a game's path or name -- are interpreted by the shell whenever any script sits in an event folder. `:104` also tests `startsWith` twice where the second should be `endsWith`, so an argument that starts with a double quote loses its last character.

**How it was found:** T35's audit (#682): L-18 (the first reader) with T2's FD-9/FD-19, confirmed with narrowing by the seat; PL-03 in `docs/audits/2026_10_31-epic-m6-es-core-window-input/05-punch-list.md` and #1337. Filed publicly with a neutral title at the coordinator's ruling (#682 comment 6542863818).

**The positive before the fix:** `window-input-tests` (3.4, `Scripting.cpp:90-113` lifted verbatim): an argument carrying `$( )` and one carrying a backtick each arrive in the command unquoted (`stage-c/build-tests.out`). **The image ships no hook** (G-01: no `/usr/bin/scripts`, no user `scripts/` folder), so the shell sees an argument only once a hook is added.

**What reading cannot prove:** which callers pass which arguments for each event (es-app's, outside the slice), and what a hook then does with them (`eval` in a hook is the hook's).

**Can this be done on the VM?** Yes -- host-only (the 3.4 case over the lifted lines); on a guest, a hook script that prints its arguments, placed in a user `scripts/<event>/` folder, shows what the shell received.
