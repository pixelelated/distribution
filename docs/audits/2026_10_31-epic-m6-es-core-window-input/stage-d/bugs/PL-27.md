## Code trace

**Where (at `16dbac5211`):** `Log.cpp:63-82`, `:101-108`, `:117-162`, `:189`

**The defect:** `close()` sets `mShutdown` under the mutex, notifies and joins; the worker swaps the buffers (`:130`), drains, flushes, and breaks when it reads `mShutdown` (`:152`) -- outside the mutex. Entries enqueued after the worker's last swap stay in the write buffer: the worker exits without another swap, and `close()` then drains the already-cleared drain buffer (`:79`, `:156-161`). #178's promise (*every batch reaches the file*, `:135-146`) does not hold at close. `mShutdown` is a plain `bool` (`:189`).

**How it was found:** T35's audit (#682): the seat's G-3, verified at the pin; PL-27 in `docs/audits/2026_10_31-epic-m6-es-core-window-input/05-punch-list.md` and #1337. The fork's logger (fork #178).

**The positive before the fix:** Read at the pin: the sequence swap (`:130`) / enqueue into the new write buffer (`:104-105`) / `close()` (`:70-71`) / break (`:152`) / `close()` drains the drain buffer (`:79`). No case has run it yet.

**What reading cannot prove:** how many lines a real exit loses (it depends on the timing of the last `LOG` against `Log::close`).

**Can this be done on the VM?** Yes -- host-only: a `Log.cpp` binary (3.23's, with the `SDL_timer.h` fake and test-defined `Settings`/`Paths` as `SystemConfTests.cpp` does) that enqueues during shutdown and reads the file.
