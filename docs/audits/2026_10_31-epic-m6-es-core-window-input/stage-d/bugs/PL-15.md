## Code trace

**Where (at `16dbac5211`):** `guis/GuiMsgBox.cpp:116-134` (`:132-133`), `:257`; `Window.cpp:1568-1578` (the dialog), `:1550-1563` (the merge), `:1622-1640`

**The defect:** `GuiMsgBox` binds back to the only button, else the first named exactly `OK` or `NO`, **else the last** (`:132-133`); `:257` also fires it for any button of an unconfigured pad. GAME DRIVE DETECTED with a drive id offers NO, IGNORE THIS TIME / NO, IGNORE FOREVER / YES, MERGE DRIVE (`Window.cpp:1568-1578`): none is named exactly `NO`, so **back takes YES, MERGE DRIVE**, whose lambda merges the drive's games, a choice that *also applies on future boots* (`:1547-1548`, `:1550-1563`). The format path asks again with NO first (`:1622-1625`), so back there binds NO. `es-ui-style-guide.md` § Confirmations: back must never land on the destructive choice.

**How it was found:** T35's audit (#682): L-12 (the first reader); the seat traced it to the drive dialog at Medium; **re-graded High as data safety** at the coordinator's stage-D ruling (#682 comment 6542863818). PL-15 in `docs/audits/2026_10_31-epic-m6-es-core-window-input/05-punch-list.md` and #1337. Upstream ROCKNIX's dialog (outside the lanes, D-UI-079) carries a destructive default, which rule 6's contained fix removes.

**The positive before the fix:** Read at the pin: the three labels at `:1569`, `:1570`, `:1577`, and `:125`'s comparison against `_("OK")` and `_("NO")`. **On the image** the accelerator lands on NO/NON where a NO exists (G-04, G-07); the drive dialog itself was not raised in the window.

**What reading cannot prove:** how often a player meets the dialog (a second card or a USB drive with games), and what `ApiSystem::mergeDrive` writes (es-app's).

**Can this be done on the VM?** Yes -- `POST /storage/event` on the guest's 127.0.0.1:1234 (`es-app/src/services/HttpServerThread.cpp:577-597`) with a `REQUEST_MERGE` line naming a disposable mount and an id raises GAME DRIVE DETECTED; `z` (back) then shows what back chose.
