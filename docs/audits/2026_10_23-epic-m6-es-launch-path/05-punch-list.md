## PL-001: A save-state launch builds the state file's path into the shell command without quoting

- **Severity:** High
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** SS-1 (`02-forward-audit.md`, group 3); G-6; both seats (`04-analysis.md` § Second opinion)
- **Owner area:** launch: the command's quoting
- **What:** At the three `-state_file` call sites, pass the path through `Utils::String::shellQuote`, the function the capture command already uses (`FileData.cpp:1148-1151`). Add a unit case that builds the command for a name containing a space, a quote and a dollar sign, and asserts the path comes back as one word.
- **Where:** `es-app/src/SaveState.cpp:77,97,111`
- **Why:** The path is built from the ROM's file name and the command goes to `/bin/sh` (`FileData.cpp:1100-1103`). On G-6 the launcher received a different path than the state file's.
- **Evidence:** proven on the guest (G-6, `exec.log:20`).
- **Can this be done on the VM?** Yes: on the lane's guest, through the shipped `es_savestates.cfg` path, with G-6's fixture (a ROM and its auto state, whose name contains a dollar sign).
- **Already written:** nothing inherited. Nothing records the command, and the state files on devices keep their names and are read as they are.
- **Acceptance:** On the guest, a launch of G-6's fixture through `POST /launch` records in `/var/log/exec.log` a `--state_file=` argument equal, byte for byte, to the auto state's path on disk. The new unit case passes in `es-unit-tests`.

## PL-002: DELETE GAME leaves a multi-file game's discs, and removes metadata files outside the game's folder

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** FD-14 (`02-forward-audit.md`, group 1, corrected by G-7); both seats
- **Owner area:** state: DELETE GAME
- **What:** In `deleteGameFiles`:
  - Call `getContentFiles()` before removing the game's own file.
  - Remove a listed file, a metadata (`MD_PATH`) file or a `.ccd` sibling only when its canonical path is inside the game's system folder, and log every path skipped.
  - In `getContentFiles`, tolerate a byte-order mark and leading white space before a `.cue` `FILE` keyword.
  - Add unit cases for the list parsing and for the containment rule.
- **Where:** `es-app/src/FileData.cpp:1386-1507` (1407-1451 the lists, 1487-1494 the metadata loop, 1503-1506 the order)
- **Why:** On G-7 the playlist was removed and its disc stayed, so the game comes back as its disc. The metadata loop removes any existing file a game's metadata names, with no check of where it is.
- **Evidence:** G-7 (only the playlist removed).
- **Can this be done on the VM?** Yes: on the lane's guest, with G-7's fixture (a psx playlist, its disc, and sentinel files inside and outside the system folder) and the GAME OPTIONS > DELETE GAME walk (`fd14/*.steps`).
- **Already written:** on devices, every earlier DELETE GAME of a multi-file game left its discs, which now list as games, and removed the art its metadata named. The fix does not touch what earlier deletes left: those discs are the player's files and stay visible as games.
- **Acceptance:** On the guest, after G-7's walk:
  - The playlist and its disc file are absent.
  - Both sentinels outside the system folder are present.
  - A second fixture game, whose metadata image names a sentinel outside the system folder, still has that sentinel after DELETE GAME.
  - The unit cases pass.

## PL-003: A sub-folder of any system is skipped when its path contains `ports` or `windows`

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** SD-2 (`02-forward-audit.md`, group 2); G-4; both seats (Argon's narrowing: the intent is the `ports` and `windows` systems)
- **Owner area:** systems: the folder scan
- **What:** In `populateFolder`, compare the system's name with `ports` and `windows`, as the two exclusions above them do (`:619`, `:623`), instead of searching the sub-folder's path.
- **Where:** `es-app/src/SystemData.cpp:626-632`
- **Why:** Lowercase `ports` or `windows` anywhere in a sub-folder's path hides that folder's games in every system.
- **Evidence:** G-4.
- **Can this be done on the VM?** Yes: on the lane's guest, with G-4's two fixture folders under `/storage/roms/gb/`.
- **Already written:** nothing inherited. The scan writes nothing for a skipped folder, so its games appear at the next scan.
- **Acceptance:** On the guest after a reboot, `GET /systems/gb/games` lists both of G-4's fixture games, and a fixture sub-folder of `/storage/roms/ports/` is still not scanned.

## PL-004: One unreadable `es_systems_*.cfg` overlay stops every later overlay from loading

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** SD-3 (`02-forward-audit.md`, group 2); G-5; Astra; Argon G-04
- **Owner area:** systems: the overlays
- **What:** In `loadAdditionnalConfig`:
  - Continue to the next file on a parse failure or a missing `<systemList>`, logging the file's name.
  - Read each directory's overlays in name order.
  - Apply the user directory's overlays after the image's.
- **Where:** `es-app/src/SystemData.cpp:1024-1095` (1039-1050 the early returns, 1026-1029 the order)
- **Why:** One bad file silently discards the player's other overrides. The order is the file system's, and the image's overlays win over the player's.
- **Evidence:** G-5.
- **Can this be done on the VM?** Yes: on the lane's guest, with G-5's two overlays (the first malformed, the second renaming a system).
- **Already written:** nothing inherited. Overlays are read at each start, and nothing records their result.
- **Acceptance:** On the guest after a reboot with G-5's overlays, `GET /systems/gb` reports the second overlay's full name, and `es_log.txt` names the malformed file.

## PL-005: A stored sort id equal to the number of sort types ends the interface when that list opens

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** SD-4 / FD-15 (`02-forward-audit.md`, groups 1 and 2); G-9; both seats
- **Owner area:** systems: the stored sort
- **What:** Change `>` to `>=` before `getSortTypes().at()`, and clamp the id where `SystemData` reads it from `es_settings.cfg`. The same off-by-one at `GuiGamelistOptions.cpp:148` belongs to the game-list options slice and is posted as a lead.
- **Where:** `es-app/src/FileData.cpp:1658-1662`; `es-app/src/SystemData.cpp:86`, `:1937-1941`
- **Why:** `std::out_of_range` ends the process (status 134 on G-9). A build with fewer sort types than the one before leaves such a value behind.
- **Evidence:** G-9, and its control at the last valid id.
- **Can this be done on the VM?** Yes: on the lane's guest, with `es_settings.cfg` edited while the interface is stopped (G-9's fixture).
- **Already written:** read both. A stored `<system>.sort` already on devices is clamped when read, so an out-of-range value becomes the default sort. Nothing to migrate.
- **Acceptance:** On the guest, with G-9's fixture (a stored gb sort equal to the number of sort types), the gb list opens and the interface's pid is unchanged afterwards; with the control value the list opens as before.

## PL-006: The boot game replays the command stored when it was chosen

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** MN-3 (`02-forward-audit.md`, group 5); both seats; Argon G-08
- **Owner area:** launch: the boot game
- **What:** At boot, build the command for `global.bootgame.path` from the current settings rather than replaying `global.bootgame.cmd`. Do the pre-launch and post-exit steps a normal launch does: the p2k conversion and the rotation record.
- **Where:** `es-app/src/main.cpp:527-572`; `es-app/src/guis/GuiMenu.cpp:11325` (the store)
- **Why:** A player who changes the boot game's core or save settings still boots the old ones, and a state argument fixed when the game was chosen is replayed after it no longer applies.
- **Evidence:** reading; both seats concur.
- **Can this be done on the VM?** Yes: on the lane's guest, with the boot game set in `system.cfg`, then a reboot, then `/var/log/exec.log`.
- **Already written:** every device with a boot game holds `global.bootgame.cmd` in `system.cfg`. Read both: the path is used and the stored command ignored, so nothing is migrated.
- **Acceptance:** On the guest, a boot game chosen while one core is set, the game's core then changed in `system.cfg`, and a reboot: `/var/log/exec.log` names the newly set core.

## PL-007: Custom-template placeholders insert names and paths without quoting, and later placeholders rewrite inserted text

- **Severity:** Medium
- **Category:** Code Quality
- **Question:** Q3 bugs
- **Source Finding:** FD-2, FD-3, FD-5 (`02-forward-audit.md`, group 1); Astra G-06, G-07; Argon G-02
- **Owner area:** launch: the command's quoting
- **What:** In `getlaunchCommand`:
  - Use `Utils::String::shellQuote` for `%GAMENAME%`, `%SYSTEMNAME%`, `%BASENAME%` and `%ROM_RAW%`, retiring `formatCommandLineArgument`.
  - Substitute all placeholders in one pass over the template, so inserted text is never scanned again.
  - Find the forced `-core`/`-emulator` options as whole words with `Utils::CommandLine`.
  - Add unit cases for each.
- **Where:** `es-app/src/FileData.cpp:528-534`, `:609-648`
- **Why:** These placeholders are reached only through a player's `es_systems_custom.cfg`; the shipped template has none (G-3). There, scraped names and file names are not quoted.
- **Evidence:** reading; G-3 for reachability.
- **Can this be done on the VM?** Yes: on the lane's guest, with a custom template under `/storage/.config/emulationstation/` and G-6's fixture ROM.
- **Already written:** nothing inherited. The command is built at each launch and not stored, except the boot game's (PL-006).
- **Acceptance:** The unit cases pass: for a name containing a space, a quote, a dollar sign and a placeholder's name, each placeholder's value comes back as one word equal to the input. On the guest, a launch through a custom template using these placeholders, with G-6's fixture, records in `/var/log/exec.log` the ROM's name as one argument equal to the file's name.
