## Source fix — 2026-10-03, M7.P1

ES `39f8883545537d5274708ea85c4683612078a957` (pushed to the fork's test/qa-integration and pinned by the distribution) reacquires the shared settings lock, compares the complete current choice with the captured text, and publishes only if it still matches. LockBusy recovery publishes nothing. This protects both load and save callers of recordLastGood.

The two new deterministic cases fail on the previous production source. After the fix, all10 cases/119 assertions pass; the image-toolchain syntax check passes. The first case retains a snapshot, lets a script publish newer live+record bytes under the lock, then resumes the real recordLastGood publication boundary through the existing friend test accessor; it does not depend on timing. The second executes the actual load with a held lock and competing temporary/record bytes. Evidence: `docs/qa-logs/2026-10-03-m7-p1/settings-before.log`, `settings-after.log`, `settings-syntax.log`. The Phase7 follow-up row names the commit. Guest race/upgrade evidence is still required, so this bug remains open.

Already written: older builds may have left an older whole record beside a newer live config. The fix records only a still-current complete choice under lock; it does not invent data missing from every surviving copy.

## First-release carry-forward — 2026-10-02 (#385)

Superseded by the 2026-10-03 source fix below. At this review the pinned ES published recovery records after loadUnderLock returned, including LockBusy; this confirmed preservation issue now carries bug so the preflight sees it. Earlier RC1/RC2 deferral stays in the historical audit. The old rc-accept exception is not renewed. Current scope: docs/rasteratops/release-readiness.md.

From the audit of the fixes to #313's items (#319, `docs/audits/2026_09_29-milestone-audit-of-the-313-fixes/02-forward-audit.md`, gpt G3-E-02, Medium): `SystemConf::recordLastGood` runs after `loadUnderLock` has returned, and on `LockBusy`, so a script publishing a new good `system.cfg` between the interface's read and its record can have its record overwritten by the interface's older recovery copy. The window is milliseconds and needs a damaged live file and a concurrent script write; the record ends older, not lost. Deferred from the release candidate's cut (`8dd6765af0`) with the second opinion's condition (D-WORKFLOW-062: *"an unresolved Medium, with explicit risk acceptance, an owner, a filed follow-up and a deterministic interleaving test in the follow-up's acceptance criteria"*). Goes with #317's release.

Owner: the interface fork (`es-core/src/SystemConf.cpp`); the script side is `001-functions`' `set_settings` and the last-good writer (`engineering-practices.md` § The last known good state is a record, D-CLOUD-078).

Can this be done on the VM? **Yes** -- `es-conf-tests` with a deterministic interleaving (a hook between the read and the record), and the guest's `system.cfg` with a script write raced against the interface's recovery by `tools/vm-serial`.

## Acceptance criteria

- [x] `recordLastGood` is taken under the same lock as the read it records, or compares the live file's identity (size and mtime, or a hash) before publishing and skips when it changed: the `es-conf-tests` case `a script's newer good state published between the read and the record is not overwritten` seen to FAIL on the code before the fix and PASS after.
- [x] The `LockBusy` path does not publish a recovery record from a read it could not lock: a second `es-conf-tests` case, seen to FAIL first.
- [x] On a guest, a script write of `system.cfg` raced against the interface's recovery (a damaged live file restored at start-up while `set_setting` writes) leaves the last-good record at the script's newer state: the record's bytes compared after the race, in `tools/vm-qa`'s `last-good` suite or a proof script under `docs/qa-frames/`.
