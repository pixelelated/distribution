## What happened

Run 100's guest-d proof, case E (`cb0b051b72`, 2026-10-02 00:29 UTC). The guest's conf named the stock `/GAMES`, and the QA cloud held nothing of ours. The startup sync's card stamped `78 no-folder`: SKIPPED - YOUR CLOUD FOLDER ISN'T SET UP YET. The guest's `cloud_sync.log` for the same second shows both halves exiting 0:

- the restore found no `/GAMES`, treated it as an empty cloud, and printed the offer line;
- the backup ran "Ensuring remote sync path exists: qa-cloud:/GAMES" and copied nine files into it (`nes/Probe.srm` and eight save states).

So the card said SKIPPED over a backup that had just made `/GAMES` and written into it. The cloud folder step that followed at the same boot (D-CLOUD-170, #363) then read `/GAMES` as holding saves and asked to MOVE it, where the design asks CREATE IT. A carried `/GAMES` is meant to count as no folder at all (D-CLOUD-161).

## Cause

`cloud_backup` makes the saves folder whenever it is absent: `rclone mkdir` on a deliberate run, and the copy itself on a `--recent` run. That is right for the current folder and for a folder of the player's own. It is wrong for a default an earlier version shipped. The restore half already declines and offers the folder, which is what the card reports.

## Decided

D-CLOUD-172. A backup does not make an absent earlier-default folder. It sends nothing and prints the restore's offer line, so the automatic card's SKIPPED is true. A deliberate run offers the folder; its seeding settles the setting on the current folders. The cloud folder step asks at the next boot.

## Can this be done on the VM?

**Yes.** The script is run whole in `tools/last-good-scripts-test` (section ad), and the boot is guest d's case E.
