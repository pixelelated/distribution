# M7.P1: Refuse cloud transfers when an existing config has no remote

Source: https://github.com/pixelelated/distribution/issues/392
Updated: 2026-10-04T21:52:26Z

## Reproduced by the #365 actor coverage

An existing empty rclone.conf passes check_rclone_config. first_remote returns an empty string and main concatenates it with the configured cloud path. The backup's legacy-folder guard then reads a local path and reports a create-folder offer plus COMPLETED instead of the setup refusal. Three new T19 actor controls fail (startup backup, exit sync, direct saves backup). Restore also constructs a local path even though its current fixture happens to fail later.

Fix both callers before any provider/path operation, retaining the existing configured-remote behavior and player-facing setup outcome. The existence of the config file is not evidence that a remote is linked.

Can this be done on the VM? Yes. Whole-script isolated fixtures precede the candidate guest proof. No personal cloud or physical-device action is needed.

Already written: affected runs can report a successful backup without a linked cloud. With a writable local-looking cloud path, they can operate on that local path. The fix must leave existing local/cloud bytes intact and refuse future calls without a valid remote prefix; no successful remote transfer can be inferred from an old completion stamp.

- [x] A writable local path supplied as the cloud path is not read or written when no remote is linked; configured-cloud controls continue to pass.
- [x] Candidate guest evidence records the refusal/outcome and unchanged bytes for direct and automatic calls.
