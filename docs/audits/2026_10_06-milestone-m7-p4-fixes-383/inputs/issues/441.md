Source: https://github.com/pixelelated/distribution/issues/441
Updated: 2026-10-05T06:52:03Z

After successful QA13 upgrade qualification, the agent attempted to rebind ten sealed, unstarted owners from QA11 to QA13. Preparation stopped before its first source write because qualify-boot.py was mode0400. The command result was not checked before the following launch: boot03 then ran its original seal and correctly failed its QA11 dependency assertion before creating any guest (actual60221/allfourrc1).

This is an orchestration error, not a failed device boot or candidate regression. QA11 remains failed; QA13's actual42880/allrc0 upgrade evidence is unchanged. No owner source was successfully rewritten; the first backup contains original source/seal bytes.

Can this be done on the VM? No physical fact is needed. Preparation checks are host-only. A fresh boot owner then performs the already planned isolated clean/upgraded VM proof using QA13's actual upgraded disk.

Already written: failed preparation traceback, original-source backup, and boot03's dependency failure receipts only. No guest boot, product or baseline mutation occurred. Preserve sealed owners and create fresh successors with explicit dependency mappings.
