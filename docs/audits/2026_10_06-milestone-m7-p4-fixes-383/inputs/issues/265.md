# M7.P5: Release versions for the fork — a SemVer scheme for release candidates, so a release is targeted by the features it carries

Source: https://github.com/pixelelated/distribution/issues/265
Updated: 2026-10-02T23:05:34Z

Maintainer, 2026-09-24 (D-QA-012, D-WORKFLOW-043): *"If, in our Git workflow, we'd like to start using versions more and take some SemVer approach to how we do this (so we can target releases more effectively with the features we hope to include), we can definitely do that, and it might be a good idea. This is the kind of thing I would include in the release following what we're working on now."*

## What exists today

- An image's identity is its **BUILD_ID**, the commit `next` was at when the build worktree synced (`build-id-is-the-synced-head`), shown on the device's info screen with the branch name. Cuts are counted in prose on the round issue ("the twenty-first cut", #236) and in `docs/vm-qa-log.md` rows.
- `tools/fork-publish-release` tags a published image `dev-<yyyymmdd>` (one release per build, not per device; the older `dev-<device>-<date>` tags predate that); re-publishing the same day replaces assets under an unchanged tag (blindspot 2).
- Upstream ROCKNIX versions its releases by date (`OS_VERSION` from `distributions/ROCKNIX/version`); the fork carries no version of its own.
- Milestones (`Stable before upstream`, `Offline RetroAchievements`, `Cloud Saves: ...`) group issues by programme, not by release.

## The task

A versioning scheme for the fork's release candidates and releases, SemVer-shaped, so that an issue can carry the version it is targeted at and a build can say which version it is a candidate for:

1. **The scheme**: what MAJOR, MINOR and PATCH mean for a fork of a date-versioned distribution (a proposal: MINOR per release candidate series, PATCH per cut within it, MAJOR reserved for the upstream base moving); where the pre-release label goes (`-rc.N`); how the version relates to BUILD_ID (both shown; the version names the intent, the id names the bytes).
2. **Where it lives**: a git tag per cut or per candidate on `next`; the version in the image (`/etc/os-release`, the info screen) beside BUILD_ID; `tools/fork-publish-release` tagging by version rather than by date.
3. **How work is targeted**: a milestone or label per version, so "what goes in 0.4.0" is a query; the round issue's contents table (#236's shape) becomes the version's changelog.
4. **The first version**: the release candidate now being cut is the reference point -- named retroactively or the first one named, the maintainer's call.

## Acceptance criteria

- [ ] A decision-register row fixes the scheme (what each component means, the pre-release form, the relation to BUILD_ID) after the maintainer's word.
- [ ] A build's image carries its version where BUILD_ID is shown today, and `tools/fork-publish-release` tags by it.
- [ ] Issues can be targeted at a version (milestone or label), and the fork's docs say how a version's contents are read.
- [ ] Applied first to the release following the one being cut now (the maintainer: *"the release following what we're working on now"*), with webkitgtk 2.54 (#228, D-WORKFLOW-042) as one of its named features.
