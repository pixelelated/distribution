# M7.P3: Discover settings archives in the per-device folders the backup writer uses

Source: https://github.com/pixelelated/distribution/issues/381
Updated: 2026-10-04T00:08:12Z

## Discovered in readiness audit #375

High; G-13, derived by following up Fable refutation A-5. Owner area: cloud scan / archive discovery. Milestone: rasteratops 0.0.1.

The current writer stores settings archives under SETTINGS_REMOTE/<device-id>/ (`cloud_backup:2037`). The restore reader deliberately selects current, legacy and previous device folders before the flat legacy root (`cloud_restore:2020–2098`). The opening scan instead performs nonrecursive `lsf --files-only` on SETTINGS_REMOTE alone (`cloud_scan:208–219`), then `GuiMenu.cpp:4855–4862` dims SETTINGS when MINE is empty.

Full production cloud_scan under the existing isolated SC fixture with real host rclone local-backend listings returns exit0, MINE empty and COUNT0 for a correctly named archive in Backups/QA-deadbeef01/. Copying those same synthetic bytes to the flat Backups root makes MINE populated. This occurs with OS_NAME=ROCKNIX, before the planned rename (#376). Host rclone is1.60.1-DEV; the candidate's rclone needs the VM regression below.

Evidence: `docs/audits/2026_10_02-milestone-375-rasteratops-0-0-1/evidence/reviewer-archive-path-probe.{sh,log}`. The existing scan fixture returns flat archive names irrespective of the path; it masks the writer/reader mismatch. This is a source/host reproduction, not a captured guest UI failure.

Already written: normal backups live in per-device folders, with older flat and healed-ID folders retained for compatibility. Preserve those bytes and the existing device-selection boundary; do not move all archives to the root or silently read another device's folder to make the scan pass. Related: #349, #350, #354, #365, #376.

## Can this be done on the VM?

Yes — GENERIC_X64 plus synthetic WebDAV/S3. Use a real production settings backup as the scan fixture; no personal cloud or physical fact is needed.
