D-CLOUD-167 supersedes the USE IT confirmation: a compatible content folder found by the scan is adopted automatically, and the chooser is offered only when none is found. ## The maintainer's words (2026-09-30, RC2 `69e6039f8f` on the Retroid Pocket Nova, Dropbox)

> The bigger issue I just hit was that I just did Content to Restore, and it seems to be showing me the root folder of my Dropbox and not checking for the Rocknix folder or letting me choose where it is.
> There are a number of issues with this:
> 1. It's showing me a bunch of unrelated things like my Hello sign directory, documents, videos, etc. Things that happen to be at the root level of my card shouldn't be showing anything if it doesn't match the types of content and the paths we're looking for.
> 2. We should be able to recognize that this isn't the right directory and should say something akin to "Please select the folder where your content is loaded," and then allow the user to select, through EmulationStation, the right path. This is not the right path. I have no way to remedy it, and it's letting me select whether or not I want to restore content totally unrelated to my gameplay experience.

## What exists today (read from `cloud_content_restore` and `cloud_setup` at `224b73ea54`)

- CONTENT TO RESTORE is built from `cloud_content_restore --scan` (`GuiMenu.cpp:4196`). The scan lists `${ROOT}ROMs/` and `${ROOT}BIOS/` (`:1243,1256`), and then **appends every top-level folder under `${ROOT}` that holds files** as a "pre-tier layout" row with no comparison and no filter (`sizes_under "${ROOT}" | grep -vE '^(ROMs|BIOS)|'`, `:1298`, emitted at `:1337-1341`). `ROOT` is the remote's root when `CONTENT_REMOTE` is empty (`:207`), so on a device whose content root is the Dropbox root the page lists the account's own folders as systems to restore.
- The filter the script's own comments promise ("Only directories this device actually has locally are offered from there -- listing somebody's holiday photos as restorable ROMs would be worse than the empty list this fixes", `:356-358` and `:398-400`) exists in `resolve_src` (`legacy_dirs`, `:404-411`) and is **not applied by `--scan`**. A name is not a behaviour (`engineering-practices.md`).
- `cloud_setup --content-location` reports `STATE=stranded-at-root|ok|empty` and `--use-content-root` sets `CONTENT_REMOTE` to empty (`cloud_setup:495-556`), and a fresh image ships `CONTENT_REMOTE="/ROCKNIX/Content"` (`cloud_sync.conf:46`). Which of these put the Nova's content root at the Dropbox root is a device read still owed (its address did not resolve from serval at the time).
- There is no row in the interface to choose the content folder: `CHANGE CLOUD FOLDER` was removed with the NETWORK SETTINGS group and "reproduced nowhere" (`engineering-practices.md` § Before deleting a duplicate). The maintainer's "I have no way to remedy it" is that gap.

Answer given at the time: restore nothing from that list; a run there would copy the listed folders under `/storage/roms/<name>/`.

## Can this be done on the VM?

**Yes.** `tools/cloud-test-backend seed-content` puts a `Photos/` and a `Documents/` folder beside `/ROCKNIX/Content` (and at the root) in the QA cloud; guest d with `CONTENT_REMOTE=""` and with the default reproduces both listings; the page's frame at 640x480 is the observation.

## Acceptance criteria

- [ ] `cloud_content_restore --scan` lists a pre-tier folder only when this device has a folder of that name under `/storage/roms` or the name is a supported system (`legacy_dirs` / `supported_systems`), the same rule `resolve_src` applies; a `tools/cloud-round-trip` case seeds `Photos/` and `Documents/` at the root and the scan's output carries neither line.
- [ ] When the content root holds no `ROMs/` and no known system folder, the page says so instead of listing: `YOUR CLOUD HAS NO ROMS OR BIOS AT <folder>.` / `CHOOSE THE FOLDER WHERE YOUR GAMES ARE?` (approved D-CLOUD-164), with a row that opens the folder chooser; a 640x480 frame shows it.
- [ ] A CHOOSE CLOUD FOLDER page (the `GuiFileBrowser` pattern fed by `rclone lsf`, `es-native-ui.md` § Reusable precedents) sets `CONTENT_REMOTE` through `cloud_setup`, and the transfer page re-reads it; the walk's frames show the chosen folder and the journal shows the `Content path` line.
- [ ] With `CONTENT_REMOTE` back at `/ROCKNIX/Content` and the QA cloud seeded with `Photos/` and `Documents/` at its root, CONTENT TO RESTORE on guest d lists only ROM systems and BIOS: the walk's 640x480 frame and the scan's output lines. (The Nova's own listing is re-read on its next staging, as a read, and noted here in a comment.)
- [ ] `docs/es-menu-map.md` carries the chooser (D-UI-039); `tools/es-menu-map-check` and `tools/vocabulary-check` pass; the cloud-sync page on the site says where the content folder is chosen (`documentation-accuracy.md`).

## Design, 2026-09-30 (D-CLOUD-156): find the folder under the cloud root before asking

The maintainer, later the same evening: *"we could be more intelligent with identifying the appropriate folder if it's not at the root, like mine isn't, because it all goes in the Rocknix directory. That's where I thought it would be looking, and so we should be scanning that."* And: *"certainly making sure we're not showing content that's not relevant to Rasteratops."*

So the chooser is the last resort, not the first answer. Added criteria, ahead of the chooser's:

- [ ] When the configured content root holds no `ROMs/` and no known system folder, the scan looks under the cloud root's `/ROCKNIX/Content` (the saves root's parent, `cloud_setup:629-631`) and, finding `ROMs/` or `BIOS/` there, uses that folder automatically and writes `CONTENT_REMOTE` (D-CLOUD-167, no USE IT confirmation); on guest d with `CONTENT_REMOTE=""` and content seeded under `/ROCKNIX/Content`, the frame sequence advances to the options and the journal shows the `Content path` line.
- [ ] Only then, with nothing found under either, the chooser opens; a frame shows it with the QA cloud's root folders listed as folders to pick from, never as systems.
