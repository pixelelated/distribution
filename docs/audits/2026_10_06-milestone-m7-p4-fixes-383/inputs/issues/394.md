## Maintainer's request

> Have we done anything to make sure that this watcher framework will be the one we use going forward with all builds?

## Behavior when opened

#393 corrects the watcher and documents its use, but launchers still opt in.
Normal native/Docker builds must use the same framework automatically,
including direct image/package entrypoints. Existing M7 build01 remains
frozen; these host tooling changes apply to future builds.

## Can this be done on the VM?

Yes: isolated host fixtures exercise the native build entrypoints, a Docker
command double and nested build processes without compiling another image.
The existing GENERIC_X64 completion supplies the monitor's live integration
proof. No physical device or personal cloud is required.

## Acceptance criteria

- [x] Native device/image/package builds and Docker build targets enter a
  common monitored runner automatically; retained routing tests catch a
  removed entrypoint hook. Interactive shells and non-build helpers retain
  their behavior.
- [x] Each top-level run retains private log, PID, atomic result and status
  plus a run-owned watcher copy. Nested package/image invocations reuse it;
  native and container paths identify the same run. The monitor includes
  buffered package logs belonging to that worktree.
- [x] Passing and injected failure controls prove return-code, argument,
  environment and output preservation, startup refusal when monitoring
  cannot arm, signal handling and durable completion/death reporting.
- [x] Canonical commands/rules and CI or push checks enforce the route;
  tracker, work log and checkpoint retain delivery and explicit notification
  limitations. No source mutation or rebuild of the frozen M7 image occurs.

Already written: existing build artifacts and their ad-hoc launch receipts
are retained. Future runs use fresh run directories; no log or result is
overwritten. Related delivery #383; watcher implementation #393.
