Title: Bug: RetroArch's `0004-drm-resolution.patch` applies to its pin only with fuzz

Found by the M6 T3 lane (#650), F-10, punch item PL-014. Low.

## Code trace

- **How it was found:** `docs/audits/2026_10_24-epic-m6-emulators-libretro/tools/q4c-patches.sh`, which applies RetroArch's 21 patches in `scripts/unpack`'s order to the files they touch at the pin `bdba046fa6`. For this patch, `patch -p1 --fuzz=0 --dry-run` and `git apply --check` both refuse, while the build's own `patch -p1` (default fuzz 2) applies it, logging `with fuzz`.
- **The defect at its source:** `projects/ROCKNIX/packages/emulators/libretro/retroarch/patches/0004-drm-resolution.patch`, whose context lines no longer match `gfx/common/drm_common.c` at the pin exactly.
- **Why it matters:** a patch held by fuzz can land on the wrong lines when the context moves. `150a4e1402` made the fork's widget patches apply at fuzz 0 for that reason.
- **The fix:** refresh the patch's context against the pin. Its added and removed lines stay the same.
- **Sibling sites hunted:** all 21 patches at the pin. Every other one applies at fuzz 0, and `batteryplus` is refused by `git apply` but accepted by `patch` at fuzz 0.
- **What reading cannot prove:** that the refreshed context changes nothing in the built file. The proof is the patched file compared before and after.

Already written: nothing; a build-time patch.

Can this be done on the VM? **n/a**: a patch check on the host.
