Title: Bug: `melonds-ds-lr` fetches eleven dependencies from the network at configure time, by short hash or tag

Found by the M6 T3 lane (#650), F-15, punch item PL-005. Medium. Blindspot 47's shape (#226, pango's cairo), through cmake.

## Code trace

- **How it was found:** `grep -rl -E 'FetchContent|ExternalProject_Add|git clone|curl |wget '` over the 111 unpacked `*-lr` sources in the M7 GENERIC_X64 build root. Four hits were read at their sites, and only this core fetches: its build directory carries `.x86_64-rocknix-linux-gnu/_deps/` with eleven `*-src` trees (date, embed-binaries, fmt, glm, libretro-common, libslirp, melonds, pntr, span-lite, yamc, zlib).
- **The defect at its source:**
  - The core's own `cmake/FetchDependencies.cmake` (lines 44 to 60 at the pin `bc4e4b67d2`) runs `FetchContent_Declare(GIT_REPOSITORY ... GIT_TAG ...)` with short hashes (`7117178`, `ad9124f`, ...) and tags (`fmt` `11.2.0`, `zlib` `v1.3.1`).
  - `projects/ROCKNIX/packages/emulators/libretro/melonds-ds-lr/package.mk` 14 to 21 passes only GL options: no `FETCHCONTENT_FULLY_DISCONNECTED`, no `FETCHCONTENT_SOURCE_DIR_<NAME>`.
- **What it costs:** a build container without network fails here, a moved tag changes the image silently, and the core links its own zlib 1.3.1 beside the image's. The core ships on all five built devices (`LIBRETRO_CORES`).
- **The fix:** carry the eleven as pinned sources, either extra tarballs with `PKG_SHA256` or packages wired through `FETCHCONTENT_SOURCE_DIR_<NAME>`, and pass `-DFETCHCONTENT_FULLY_DISCONNECTED=ON`, so a missing one fails the configure by name.
- **Sibling sites hunted:** the other three hits:
  - `b2-lr`: a Makefile maintenance target, not a build step;
  - `mojozork-lr`: SDL3 behind `MOJOZORK_SDL3`, unset for the libretro build;
  - `skyemu-lr`: a bundled curl from the tarball.

  None has a `_deps` directory.
- **What reading cannot prove:** the exact bytes the fetches gave this image's build.

Already written: nothing on devices; a build-reproducibility defect.

Can this be done on the VM? **n/a**: a build property. The proof is a build of the core with no network, and an empty `_deps` find.

## Acceptance criteria

- [ ] `melonds-ds-lr/package.mk` passes `-DFETCHCONTENT_FULLY_DISCONNECTED=ON` and names every dependency with a full hash and a checksum.
- [ ] A build of the core in a container with no network configures, and `find <root>/build/melonds-ds-lr-*/.*/_deps -name '*-subbuild'` prints nothing.
