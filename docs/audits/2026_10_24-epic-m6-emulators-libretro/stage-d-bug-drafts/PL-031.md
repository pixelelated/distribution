Title: Bug: every built launch table offers RetroArch's `ffmpeg` core for the media player, and no image installs it

Found by the M6 T3 lane (#650) in Phase 4.6, by the table-against-image comparison that grading both seats' G-01 called for. Punch item PL-031. Low.

## Code trace

- **How it was found:** every `retroarch` `<core>` of the GENERIC_X64, H700 and SM8550 images' `es_systems.cfg` was checked against each image's `usr/lib/libretro/`. All three name `ffmpeg` under `mplayer`'s `retroarch` emulator, and none carries `ffmpeg_libretro.so`.
- **The defect at its source:** `virtual/emulators/package.mk:1708`, `add_emu_core mplayer retroarch ffmpeg false`, sits beside the default `mplayer mplayer mplayer true` (1706). Choosing the RetroArch emulator for a video makes `runemu.sh:302` load `-L /tmp/cores/ffmpeg_libretro.so`, which no package installs.
- **The fix:** drop line 1708, or build the core where the choice is kept.
- **Sibling sites hunted:** all three images (above), and PL-030 for GENERIC_X64's own skipped cores.
- **What reading cannot prove:** RetroArch's message on the failed load. The guest run shows it.

Already written: nothing beyond a per-game choice, which falls back to the default once the line is gone.

Can this be done on the VM? **Yes.** On the guest, the RetroArch emulator is chosen for a video file in `mplayer`, and `/var/log/exec.log` is read for the failed core load.

## Acceptance criteria

- [ ] No table from `tools/regen-es-systems.sh` names a `retroarch` `ffmpeg` core that its device's install tree lacks.
- [ ] The guest's `mplayer` system lists only the `mplayer` emulator, read from its `es_systems.cfg`.
